# 03 AI Agent 协作规范

## 1. 目标与适用范围

本规范用于协调产品、架构、设计、内容、Android 功能、测试、安全和发布 Agent。目标不是增加流程，而是让多个 Agent 能在不覆盖彼此工作、不臆造接口、不遗漏验证的前提下并行交付。

角色是职责边界，不要求每个角色都对应一个独立模型或实例。同一会话可以承担多个角色，但同一任务的执行者与最终验收者应尽量分离；协调者不能用自己的实现替代独立 QA 证据。

## 2. 唯一事实来源

| 信息 | 事实来源 | 不允许的做法 |
| --- | --- | --- |
| 用户需求和优先级 | `01-PRD.md`、用户明确指令 | 根据技术便利性自行删需求 |
| 模块边界与技术选型 | `02-ARCHITECTURE.md`、ADR | 在功能任务中静默更换架构 |
| 内容和插件格式 | `05-DATA-CONTENT-PLUGIN.md` | 各模块自定义同名异义字段 |
| 任务范围与依赖 | `04-WBS.md`、独立任务卡 | 只凭聊天印象认领工作 |
| 测试门禁 | `06-TESTING-ACCEPTANCE.md` | 以构建通过代替行为验收 |
| 安全与隐私 | `07-SECURITY-RELEASE.md` | 为演示方便关闭安全检查 |
| 当前进度 | 任务卡、交接记录、实际提交 | 只写“基本完成”或口头估计 |

优先级冲突按 README 的效力顺序处理。低优先级文档与高优先级文档不一致时，应修正文档，而不是任选其一。

## 3. 角色与职责

| 角色代码 | 职责 | 可交付 | 无权单独决定 |
| --- | --- | --- | --- |
| COORD | 拆解、排期、依赖、认领、冲突协调、里程碑验收 | 任务卡、依赖图、集成结论 | 篡改测试证据、绕过安全门禁 |
| PRODUCT | 用户场景、需求、文案、优先级 | PRD、需求验收样例 | 未评审的公开技术契约 |
| ARCH | 架构、模块、接口、版本和 ADR | 架构文档、接口契约、ADR | 将未验证选型宣称为定论 |
| DESIGN | 设计系统、页面状态、动效和可访问性 | Compose 组件、设计规范、UI 测试 | 自行修改业务数据语义 |
| CONTENT | 知识树、术语、双语示例、内容审查 | 内容包、来源和审查记录 | 把 AI 草稿直接作为已审内容 |
| DATA | Room、FTS、导入、迁移、离线索引 | Schema、DAO、迁移和测试 | 修改插件安全策略 |
| LEARN | 知识树、学习路径、进度、详情 | 学习功能与关联跳转 | 私改词典/下载内部实现 |
| DICT | 搜索、排序、术语详情、双语模式 | 词典功能与搜索测试 | 降低精确匹配优先级以掩盖问题 |
| TERMINAL | 会话、沙箱、命令、诊断、补全、运行时 | 终端功能、资源控制与测试 | 开放任意系统 shell 或路径 |
| AI | Provider、流式会话、上下文和密钥设置 | AI 功能、Mock 测试、隐私提示 | 让模型回答自动执行命令 |
| PLUGIN | 包导入、校验、依赖、注册、卸载 | 插件功能、安全测试 | 首版导入可执行代码 |
| QA | 测试计划、追踪矩阵、集成和回归 | 测试报告、缺陷、验收结论 | 为通过验收而降低既定标准 |
| SEC | 威胁模型、密钥、插件/终端安全审查 | 安全报告、阻断项、修复建议 | 用扫描无报错代替人工审查 |
| RELEASE | 构建、签名流程、制品、发布和回滚 | 可重复构建、发布记录 | 发布含失败测试或秘密的产物 |

## 4. 任务粒度与拆分规则

一个执行任务应满足：

- 一个明确行为或契约，预计工作量约 0.5–2 个开发日。
- 只有一个当前负责人，修改范围可列举，结果可独立验证。
- 有输入、输出、依赖、非目标和至少一个可能失败的验收用例。
- 能独立评审；若必须同时修改多个功能，应先拆出契约任务和集成任务。

以下情况必须继续拆分：

1. 同时包含“实现整个终端”“完成所有 AI 功能”等宽泛目标。
2. 同时需要两个以上互不依赖的功能页面。
3. 验收只能写成“正常工作”“体验良好”而没有可观察结果。
4. 任务等待外部条件，却仍有大量可独立完成的内部工作。
5. 公共接口与多个实现混在同一任务。

拆分顺序：**契约/数据 → 核心逻辑 → UI/入口 → 集成 → 测试与文档**。不要先各自实现 UI，再在集成阶段猜测数据格式。

## 5. 任务卡与状态机

### 5.1 必填字段

任务卡使用 `docs/templates/TASK_CARD.md`，至少包含：

- 任务 ID、标题、优先级、负责人和评审人。
- 用户价值、目标、非目标、依赖和允许修改的路径。
- 输入契约、输出契约、共享文件和兼容性影响。
- 验收条件、测试命令、证据位置和回滚方式。
- 状态、阻塞原因、交接位置和文档更新。

### 5.2 状态定义

```text
Backlog → Ready → In Progress → Review → Testing → Done
              ↑         │           │        │
              │         └→ Blocked ←┘        │
              └────────── 重新认领/补充范围 ←──┘
```

| 状态 | 进入条件 | 离开条件 |
| --- | --- | --- |
| Backlog | 已记录需求，但输入或依赖不完整 | 任务卡和依赖齐备 |
| Ready | 可执行、无未满足前置、范围明确 | 唯一负责人声明认领 |
| In Progress | 正在实现或本地验证 | 自测完成提交评审，或遇到阻塞 |
| Blocked | 缺失条件已具体记录 | 阻塞解除并重新核对范围 |
| Review | 代码/内容和自测证据可评审 | 评审通过或退回修改 |
| Testing | 独立集成/设备/安全验证中 | 全部门禁通过或退回 |
| Done | 验收、测试、文档和交接全部完成 | 仅可因新缺陷另建任务重开 |

**禁止状态跳跃**：没有测试证据不能从 In Progress 直接到 Done；Blocked 不能表示完成；只完成静态页面不能表示业务功能完成。

## 6. Definition of Ready（DoR）

协调者把任务置为 Ready 前必须确认：

- 对应 PRD 需求编号和 WBS 编号存在。
- 所有前置任务已 Done，或其输出契约已冻结并有稳定替身。
- 需要修改的目录没有未解决的所有权冲突。
- 外部服务、设备和密钥是否可用已经明确；不可用时有获批的测试边界。
- 验收条件来自需求，而非将实现方案复述一遍。
- 回滚和兼容性要求已识别。

## 7. Definition of Done（DoD）

只有全部满足才能 Done：

1. 任务内所有验收条件有实际结果。
2. 正常、边界、失败和取消路径按风险得到验证。
3. 没有新增未解释的失败测试、静态检查错误或严重告警。
4. 跨模块入口真实接线，没有只存在函数、按钮或类型定义的情况。
5. 数据迁移、插件兼容、权限和隐私影响已处理或明确不在范围内。
6. 文档、任务状态、测试证据和交接记录更新。
7. 评审人与 QA 对各自门禁签字；执行者自报完成不等于验收完成。

## 8. 认领与所有权协议

### 8.1 认领消息

```text
CLAIM
Task: CT-400-04
Owner: TERMINAL
Goal: 实现安全命令解析与白名单执行
Dependencies: CT-000-04, CT-010-02, CT-400-02
Owned paths: runtime/safe-shell/**
Shared paths: 无
Acceptance: TRM-002、TRM-006 对应任务卡用例
Expected handoff: 实现 + 单元测试 + 安全负例
```

认领后把任务状态改为 In Progress。若发现已有未登记改动，先停下核对，不覆盖、不回退。

### 8.2 文件和目录所有权

- 执行 Agent 对任务卡列出的路径拥有临时修改责任，不代表可以重写他人已有实现。
- `settings.gradle`、Version Catalog、导航总表、数据库 Schema、公共主题和插件 API 属于共享高冲突区域。
- 修改共享文件前发送 `SHARED_EDIT`，说明文件、原因、预期字段和冲突窗口。
- 两个并行任务必须改同一共享文件时，由 COORD 指定一个集成负责人，其他 Agent 提供最小补丁或明确修改请求。
- 禁止通过整文件覆盖、格式化全仓库或重排无关代码制造冲突。

## 9. 并行协作策略

### 9.1 可并行条件

- 输入契约已冻结，或有明确版本和测试替身。
- 修改路径不重叠，公开行为不会互相改变。
- 各自能独立测试，不依赖对方未提交文件。
- 集成点和最终负责人已指定。

### 9.2 推荐工作流

| 工作流 | 前期任务 | 后期任务 | 必须同步的契约 |
| --- | --- | --- | --- |
| A 基础体验 | 工程、设计令牌、导航、通用状态 | 引导、深色模式、可访问性 | 路由、组件状态 |
| B 内容学习 | Schema、数据库、种子内容、搜索索引 | 知识树、词典、双语、进度 | 内容 ID、关联关系、错误模型 |
| C 离线与插件 | 包规范、校验、安装事务 | 下载、存储、导入、启停 | 清单、版本、依赖、文件布局 |
| D 终端 | 沙箱、解析器、会话模型 | 高亮、诊断、补全、运行时 | Runtime SPI、资源和权限策略 |
| E AI | Provider、密钥、Mock 流式响应 | 对话、上下文、错误恢复 | AiRequest、ContextDraft、取消语义 |
| F 质量发布 | 测试基础设施、威胁模型 | 集成、设备、性能、安全、发布 | 门禁和证据格式 |

### 9.3 集成节奏

- 契约变化随时同步，功能分支按里程碑集成，避免长期隔离。
- 每次集成只引入一组可解释变化；失败后先定位，不批量合并更多变更。
- M2、M3、M4 设置接口冻结点；冻结后变更必须走 `CONTRACT_CHANGE`。

## 10. 契约变更协议

任何 Agent 发现跨模块接口需要修改时提交：

```text
CONTRACT_CHANGE
ID: CC-终端-001
Requester: TERMINAL
Current contract: RuntimeSession.cancel() 仅取消协程
Proposed change: 同时保证底层进程终止，并返回可观察状态
Reason: 页面退出后进程仍可能运行
Affected modules: runtime:api、feature:terminal、QA
Compatibility: SPI 行为变更，需提升 minor 版本并补测试
Required reviewers: ARCH、SEC、QA
Migration/rollback: 保留旧适配器一个里程碑；失败恢复旧实现
```

在 ARCH 与受影响负责人确认前，只允许在本地草案中实验，不得让其他模块依赖未确认接口。变更通过后同步更新 ADR、接口文档、生产端、消费端和测试。

## 11. 交接协议

以下情况必须交接：任务完成、跨角色流转、会话即将结束、遇到阻塞、连续失败需要换方向、发现范围外问题。

使用 `docs/templates/HANDOFF.md`，内容必须能让未参与前文的 Agent 继续，不允许只写“见上面聊天”。

### 11.1 最小交接消息

```text
HANDOFF
Task: CT-500-03
Status: Blocked / Review / Testing
Completed: Provider 接口与 Mock SSE 解析
Files: feature/assistant/...（列出真实文件）
Contracts: 未变 / 指向 ADR
Verification: 命令、环境、退出状态、关键结果
Remaining: 真实服务人工验收；取消竞态测试
Risks: 不得宣称真实 API 已验证
Next owner: QA / AI / ARCH
```

### 11.2 接收确认

接收者先复述当前可观察状态、剩余目标和第一项动作，再修改文件。若交接证据与仓库状态不一致，以实际文件和测试为准，并记录差异。

## 12. 阻塞与失败处理

### 12.1 阻塞分类

| 类型 | 示例 | 动作 |
| --- | --- | --- |
| 需求阻塞 | 两种交互结果冲突 | PRODUCT 提供具体决策，其他不受影响任务继续 |
| 契约阻塞 | 插件字段语义不清 | ARCH 组织 ADR，先使用明确边界的测试样例 |
| 环境阻塞 | 无 Android SDK、模拟器或设备 | 完成可独立验证部分，明确未验证项 |
| 外部服务阻塞 | AI 服务不可用、无密钥 | 使用 Mock 验证内部边界，真实联调保持待办 |
| 权限/安全阻塞 | 需要秘密、签名或额外权限 | 不绕过、不打印秘密，提交给授权者 |
| 技术阻塞 | 同一问题多次失败 | 保存最小复现、日志和已排除假设，请求配对诊断 |

### 12.2 失败纪律

- 每次重试必须有新假设、新证据或不同验证路径。
- 不得通过删除测试、放宽断言、硬编码成功结果或隐藏错误让门禁变绿。
- 网络写请求结果未知时先查询状态，不盲目重发。
- 同一失败连续两次且没有新增信息时，暂停该方向并请求 ARCH/相关角色复核。
- 部分完成时列出具体完成项和剩余项，任务保持 In Progress 或 Blocked。

## 13. 评审协议

### 13.1 执行者自审

- 对照任务卡逐项检查目标和非目标。
- 查看完整差异，寻找孤立实现、未接线入口、无关改动和调试残留。
- 验证错误、空、取消、重复调用和恢复路径。
- 确认测试能失败：至少核对测试覆盖了需求行为，而非只断言未崩溃。

### 13.2 代码/内容评审

评审意见分为：

- **Blocker**：安全、数据丢失、秘密泄露、核心行为错误，必须修复。
- **Major**：验收缺失、兼容问题、跨模块违约，必须修复或正式变更范围。
- **Minor**：局部质量和可维护性问题，修复后再合并。
- **Suggestion**：非阻断建议，不得借此无限扩大任务。

评审必须引用文件、行为和需求编号，不只写“优化一下”。内容评审还需检查术语准确性、代码版本和预期输出。

### 13.3 QA 独立验收

QA 从需求推导用例，并检查需求追踪矩阵。实现 Agent 可以提供测试建议，但不能要求 QA 只验证实现已经支持的路径。

## 14. 分支、提交与合并

- 分支建议：`feature/CT-400-04-safe-command-parser`；修复：`fix/BUG-TRM-001-...`。
- 一个提交表达一组内聚变化，提交说明包含任务 ID 和行为，不写“update”“fix”等无信息文本。
- 不提交密钥、真实用户对话、临时解包目录、构建缓存或无关生成物。
- 不强制推送共享分支，不绕过 hooks，不通过重置历史掩盖失败。
- PR 关联任务卡、需求、测试证据和契约变化；无真实设备验证时明确标注。
- 合并后由指定集成者运行集成测试，单个 PR 成功不替代里程碑验收。

## 15. 沟通与上下文纪律

派发给 Agent（智能体）的上下文应包含：背景、用户价值、已有事实、已排除方向、任务 ID（标识）、准确路径、契约、非目标和期望输出，并使用 `docs/templates/AGENT_DISPATCH.md` 生成派发消息。不要把整段无关聊天全部转发，也不要只给“根据你的发现继续修”这种无法独立执行的话。

Agent 返回摘要应区分：

- **观察**：实际文件、命令、测试或设备结果。
- **推断**：基于证据但尚未验证的解释。
- **未知**：缺失条件和待验证行为。

不得虚构工具执行、文件路径、命令输出、测试通过率、真实 API 结果或设备截图。

## 16. 安全与隐私纪律

- 只使用秘密路径或注入句柄，不读取、打印或传播秘密正文。
- 测试使用假密钥和本地 Mock；CI 不依赖真实商业 API。
- 导入包一律视为不可信输入，执行 zip 路径、大小、数量、签名和依赖检查。
- 终端命令不直接拼接系统 shell，AI 输出不自动执行。
- 调试日志默认脱敏；上下文发送、导出和分享需要用户主动行为。
- 安全审查未通过时，交付流程停在安全门禁，COORD（协调者）将任务退回修复；发布候选不进入发布阶段。

## 17. 协调者里程碑检查清单

1. 所有 P0 需求均映射到已 Done 任务和测试。
2. 无未处理的 Blocker/Major，无隐藏的 Blocked 任务。
3. 公开契约、Schema、插件 API 和依赖版本一致。
4. 构建、集成、设备、安全和离线恢复证据齐全。
5. 文档与真实实现一致，未实现能力仍标记为后续版本。
6. 发布包不包含秘密、临时文件、测试后门和未审查插件。
7. 已知限制和回滚路径已写入发布记录。

## 18. 推荐执行规则摘要

> 先契约、后并行；先认领、后修改；一个任务一个负责人；跨模块先协调；失败要有证据；完成必须可验收；任何 Agent 都不能把自己的推测写成事实。
