## 背景

`docs/02-ARCHITECTURE.md` §6 规划了 Room + Room FTS + DataStore 的本地数据方案；`docs/04-WBS.md` 的 CT-010-02 要求建立 Room 实体、DAO、FTS 与迁移策略。但当前约束发生变化：

- 本机是 aarch64 手机 proot、低内存（约 1.4GB），Room 需要 KSP/注解处理，构建内存与时间开销显著，且首次构建需要下载更多依赖。
- MVP 首版只需要“加载一个预构建内容包 → 内存索引 → 完成离线学习闭环 → 本地保存进度与设置”，不需要数据库事务、迁移与 FTS 扩展即可支撑。
- 知识内容由 content-a/content-b 以 JSON 形式产出（`content/packs/**`），打包工具生成 `.codepack` 与 catalog；内容规模在 MVP 是 12 个领域包，单包数十节点/术语，内存索引完全可行。
- 进度与设置是少量键值数据，DataStore Preferences 足够；NFR-003 只要求“失败不破坏既有可用内容、升级可迁移”，并不强制 Room。

## 决策驱动因素

- **低内存设备可构建**：减少注解处理与依赖，缩短构建时间、降低 OOM 风险（与 ADR-001、ADR-009 一致）。
- **首版闭环优先**：MVP 的验收是学习闭环，不是数据库架构；先交付可验证的离线路径。
- **可迁移**：稳定 ID 与内容 Schema 不依赖具体存储；后续引入 Room 时按稳定 ID 迁移进度与设置。
- **可测试**：内存索引与搜索排序可在纯 JVM 单测中覆盖，不依赖 Android instrumentation。

## 候选方案

| 方案 | 优点 | 代价/风险 | 验证结果 |
| --- | --- | --- | --- |
| A：预构建 JSON 内容包 + 内存索引 + DataStore（进度/设置） | 构建开销小；纯 JVM 可测；首版闭环最快；无迁移风险 | 全量内容驻留内存；无 FTS；大数据量性能需要上限保护；后续迁移需要设计 | 采用；性能上限通过 NFR-002 目标验证（10,000 术语受控内存索引） |
| B：MVP 直接上 Room + FTS（按原 `docs/02` 计划） | 长期架构稳定；FTS 性能好 | KSP 构建成本与内存风险；需要 Schema/迁移/DAO 全部先落地；低内存设备验证周期长 | 推迟到 M2 评估 |
| C：SQLite 手写 DAO（不用 Room） | 比 Room 轻 | 需要自行处理线程/事务/迁移，易出隐蔽缺陷；与团队熟悉度不符 | 不采用 |
| D：全部放 DataStore（含内容） | 依赖最少 | 内容规模与查询能力不匹配；搜索排序不可行 | 不采用 |

## 决策

1. **内容来源**：MVP 使用预构建 JSON 内容包（仓库根 `content/packs/<packId>/`，打包成 `.codepack` 分发）。应用内置种子内容通过 `:app` assets 引入；导入包经 `:plugin-api` 校验后安装到应用私有目录。
2. **内存索引**：`:core:domain` 提供只读内容模型与索引/搜索接口（纯 JVM），`:core:data` 负责加载 JSON 并构建内存索引（图、术语、示例、语法）；查询在主线程外执行，快速连续查询取消旧查询。
3. **进度与设置**：学习进度（未学/学习中/已掌握）、最近位置、设置（语言模式、主题、字号、减少动效、AI 配置的非密钥部分）用 DataStore Preferences 持久化；密钥密文按 ADR-004 单独存放。
4. **安装状态**：安装状态机按 `docs/05` §9 实现，`activeVersion` 原子切换；状态记录与文件一致性在启动时校验。MVP 不引入数据库事务，改用“暂存目录 + 原子重命名 + 状态文件”实现等价语义。
5. **Room/FTS 推迟**：M2 评估以下条件后再决定迁移：术语规模接近 10,000 时内存索引的 P95 与内存占用是否达标；是否需要 FTS 的复杂查询；进度数据量是否超出 DataStore 合理范围。评估前不引入 Room/KSP 依赖。
6. **迁移影响记录**：稳定 ID 是迁移锚点；进度记录的 `topicId`/`termId` 不随包更新改变；内容包更新以 `replacedBy`/tombstone 迁移进度。迁移到 Room 时新增 Schema v1、一次性导入 DataStore 与内存索引，失败回退保留 DataStore 数据。

## 理由

- 低内存设备上 KSP + Room 的构建成本与失败风险会直接威胁 MVP 的“可构建、可出包”目标；ADR-009 已把 `:core:domain` 定为纯 JVM，内存索引能复用同一份单测与黄金路径用例。
- 数据量与查询复杂度在 MVP 范围内可控，NFR-002 的 10,000 术语目标可以用受控候选上限、规范化键与排序层级达成，不需要 FTS 才能满足。
- 稳定 ID 与 Schema 版本独立于存储，迁移路径清晰，不会因为推迟 Room 而制造后续无法处理的兼容债务。

## 后果

### 正面

- 构建更快、依赖更少，低内存设备与 CI 都更容易通过。
- 内容、索引、搜索排序可在纯 JVM 中单测，符合“无 Android SDK 也能验证核心逻辑”。
- 安装状态与内容版本的一致性规则清晰，不依赖数据库事务训练。

### 负面与限制

- 全量内容驻留内存，内容量增大时内存与启动时间上升；需要明确的包大小与条目上限（`docs/specs/knowledge.md`）。
- 没有 FTS：中文分词、复杂检索能力受限；MVP 用规范化键 + 前缀 + 受控模糊匹配覆盖 PRD 的排序层级。
- 后续迁移到 Room 需要一次兼容性设计、迁移测试与回滚方案，不能“边写边换”。

### 对其他模块的影响

- `:core:data` 负责 JSON 加载/校验/安装与 DataStore；`:core:domain` 定义模型与索引接口（纯 JVM）。
- `feature:learn`/`feature:dictionary` 只依赖仓库接口，不感知存储实现；UI 组合内容与进度，不把学习状态写回内容包。
- 内容工具（`tools/content`）必须保证 JSON Schema 稳定，否则迁移成本上升。
- QA 需要覆盖：内容包更新、进度迁移、安装失败回滚、飞行模式离线读取、搜索排序。

## 兼容与迁移

- **内容版本**：`schemaVersion`（当前 1）与包 `version`（SemVer）分离；主版本变更才允许破坏性字段改动。
- **进度迁移**：内容包更新时按稳定 ID 保留进度；删除节点写 tombstone 或 `replacedBy`，UI 显示“内容已更新”而不是静默丢失。
- **存储迁移（未来 Room）**：新 Schema v1 + 一次性导入 + 校验；失败时保留 DataStore 原数据与旧索引，应用继续可用；迁移开关由新 ADR 控制。
- **回滚条件**：内存索引在真实内容包上出现启动时间或内存不可接受时，提前启动 Room 评估（把 M2 评估前移）。

## 验证计划

- 纯 JVM 单测（`:core:domain:test`）：图/词典索引构建、搜索排序层级与取消、进度模型与 tombstone 迁移、安装状态机转移。
- 集成测试（`:core:data` 或应用内）：内容包加载失败回滚、`activeVersion` 原子切换、飞行模式读取、DataStore 读写与重启恢复。
- 性能：10,000 条术语受控数据下记录设备、数据量、P50/P95 与内存峰值；达标后写入 QA 报告。
- 推翻条件：受控数据下搜索 P95 超过 300ms 且无法通过索引/上限优化解决，或内存峰值超出设备预算。
