## 背景

知识树是 CodeTree 的主入口。PRD 要求：图谱支持缩放、拖动、节点选择和回到当前位置；边类型包含前置、相关、应用和易混淆，且不能只依赖颜色区分；大型图谱不能无界渲染。`docs/02-ARCHITECTURE.md` §7 进一步要求图遍历维护 visited 集、允许有向图与交叉关联、采用视口裁剪或分层加载。

已确认事实：

- UI 技术栈为 Jetpack Compose（Compose BOM 2024.09.02），`feature:learn` 为独立 Android 模块。
- 图形数据由纯 JVM 的 `:core:domain` 提供只读图谱，`feature:learn` 不得直接访问内容文件或数据库。
- 首版图谱规模：种子内容包合计 12 个领域、单包数十个节点，预计单屏可见节点量级在数十到数百；远期目标 10,000 条术语不直接等价于图谱节点数。
- 低内存设备（约 1.4GB 可用内存）不适合引入重量级原生/Web 图形引擎。

## 决策驱动因素

- **体积可控**：APK 不额外引入第三方图形库或 WebView 依赖。
- **离线可用**：不依赖远程渲染资源、字体或 JavaScript。
- **可测试**：布局与视口计算应能用纯 JVM 单测覆盖，不依赖设备截图。
- **可访问性**：图形交互之外必须提供等价的列表/详情入口，关系不能只靠颜色区分。
- **安全面**：不引入 WebView/JS 引擎，避免新的不可信输入面。

## 候选方案

| 方案 | 优点 | 代价/风险 | 验证结果 |
| --- | --- | --- | --- |
| A：Compose `Canvas` 自绘分层图（布局在 `:core:domain` 计算，UI 只做变换与绘制） | 无第三方依赖；布局可纯 JVM 单测；视口裁剪、LOD、手势完全可控；体积与内存可控 | 需要自行实现布局、裁剪、命中测试与图例 | 待 TASK-106/107 实现后以单测覆盖布局算法与视口裁剪 |
| B：引入第三方图可视化库（如 GraphView 或 Compose 图形库） | 开发快 | 体积增加、维护不可控、API 与 Compose 2.0/AGP 8.6 兼容性未知、离线与可访问性受限 | 未验证，不采用 |
| C：WebView + JavaScript 图库 | 生态成熟、交互丰富 | 增加 WebView 安全面与内存开销；离线资源打包复杂；与“苹果式极简、原生体验”冲突 | 未验证，不采用 |
| D：纯列表/树形控件，不做图形 | 实现最简单 | 不满足 LRN-001 的缩放、拖动与回到当前位置 | 不满足需求，不采用 |

## 决策

采用 **Compose Canvas 自绘分层图**，并遵守以下契约：

1. **数据与布局分离**：`:core:domain` 提供 `GraphLayout`（纯 Kotlin 数据），输入为节点、边与视口参数，输出节点坐标、层号、边路径点；布局算法可单元测试，不依赖 Android。
2. **分层策略**：以 `prerequisite` 边做最长路径分层（源节点在前置层之前），`related`/`appliedIn`/`confusedWith` 参与层内排序与跨层连线；检测循环，循环边降级为 `related` 展示方向并在内容校验中报告，不阻塞渲染。
3. **视口裁剪**：只绘制与当前视口（含边距）相交的节点与边；按缩放级别做标签 LOD（低缩放只画节点与边，高缩放显示标题），单帧绘制节点数设上限，超出时降级为“聚焦当前节点 + 邻域”。
4. **交互状态**：缩放（双指/按钮）、拖动（单指平移）、节点选中（点击命中，命中半径至少 24dp）、回到当前节点（动画平移，减少动效时直接跳转）；状态由 `LearnViewModel` 的单一 `UiState` 持有，禁止在 Canvas 内部维护不可恢复的独立状态。
5. **关系可识别**：四类边使用不同线型（实线/虚线/点线/双线）加图例文字，颜色只作辅助；节点选中、前置、易混淆有独立形状或角标。
6. **等价入口**：节点详情页提供“关联节点列表”，与图形视图共享同一份关系数据；TalkBack 可遍历列表完成同等任务。

## 理由

- 自绘方案把复杂度留在纯 JVM 的布局算法上，可用 `:core:domain` 的 JUnit 5 单测覆盖分层、循环、视口裁剪与命中测试，不需要模拟器即可获得证据，符合低内存设备验证约束。
- Compose `Canvas` 与设计系统共用色彩、字体与动效令牌，保持“苹果式极简”的统一观感；不引入 WebView 也避免了额外的安全评审面。
- 分层 + 视口裁剪 + LOD 是 `docs/02-ARCHITECTURE.md` §7 的直接落地，能满足“大图不无界渲染”的验收条件。

## 后果

### 正面

- 零第三方图库依赖，APK 体积与构建内存可控。
- 布局算法可测试、可复用（未来列表模式、路径视图共享同一份图数据）。
- 交互与动效完全受设计系统控制，减少动效降级容易实现。

### 负面与限制

- 需要自行实现命中测试、缩放锚点、边路由与标签避让，工作量集中在 TASK-106/107。
- 超大图（数千节点同屏）不追求全量绘制，首版以“聚焦邻域”降级，需要在 UI 上给出明确提示。
- 边路由不做正交布线，交叉边较多时可读性受限；通过图例、线型与筛选缓解。

### 对其他模块的影响

- `:core:domain` 新增图布局与视口计算 API，`docs/specs/module-layout.md` 中列为 `com.codetree.domain.graph`。
- `feature:learn` 依赖 `:core:designsystem` 的动效令牌与 `:core:domain` 的布局模型，不新增第三方依赖。
- 知识内容格式需保证边类型与方向语义完整（见 `docs/specs/knowledge.md`），否则布局降级规则会误判。

## 兼容与迁移

- 图谱布局是纯展示层计算，不写数据库、不改变内容 Schema；后续替换为其他布局算法时，内容包与进度数据无需迁移。
- 若未来引入更高性能布局（如预计算坐标随内容包分发），需修订本 ADR 并在内容 Schema 增加可选字段，遵循 `schemaVersion` 升级规则。
- 回滚条件：布局在真实内容包上出现不可接受的性能问题（缩放/拖动持续掉帧）且视口裁剪无法缓解时，回退到“按领域分组的两层视图”，并记录证据。

## 验证计划

- 单元测试（`:core:domain`）：空图、单节点、多根、交叉关联、自环与多节点循环、前置缺失、视口裁剪边界、命中测试半径。
- UI 验收（`feature:learn`）：真机/预览中验证缩放、拖动、选中、回到当前节点；TalkBack 能通过列表完成关联跳转；减少动效开启后无位移动画。
- 性能：记录设备、节点数、单帧绘制节点数与缩放/拖动帧率，写入 QA 报告。
- 推翻条件：Compose Canvas 在目标设备上无法维持基本交互帧率，或视口裁剪无法把单帧绘制量压到可接受范围。
