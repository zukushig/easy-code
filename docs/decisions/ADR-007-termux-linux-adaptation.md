## 背景

`docs/01-PRD.md` 的 TRM-008 把“Termux 或完整 Linux 适配”列为 P2；`docs/02-ARCHITECTURE.md` §11 与 `docs/04-WBS.md` CT-400-12 要求独立 ADR、威胁模型和发行政策。社区对“在手机上写代码”的预期常包含完整 Linux 工具链（apt、gcc、python、node、git 全命令），但 CodeTree 的 P0 定位是**受控学习环境**，不是 Linux 发行版。

已确认事实：

- CodeTree 运行在普通 Android 应用沙箱内，不具备 root、PTY、进程隔离或系统包管理权限。
- `docs/07-SECURITY-RELEASE.md` §4.2 已要求：Python、JavaScript、Termux 或 Linux 支持需要独立 ADR 与威胁模型，至少评估网络、子进程、文件访问、原生依赖、资源限制、第三方许可和商店政策；评审完成前 P0 沙箱规则保持启用。
- MVP 的终端能力由 ADR-003 的 safe-shell 提供，与 Termux/Linux 是**不同能力**，不得混为一谈。

## 决策驱动因素

- **用户预期管理**：如果把“终端”宣传成完整 Linux，用户会期待 apt/gcc/管道/后台任务，实际无法交付，属于产品欺骗。
- **安全边界**：完整 Linux 意味着任意二进制执行、网络、文件系统与包管理，需要独立沙箱与威胁模型，不能在 proot/手机应用沙箱里承诺。
- **资源与体积**：完整发行版会带来数百 MB 级体积、启动内存与电池消耗，与低端设备兼容目标冲突。
- **合规**：内嵌 GPL/其他许可工具链、第三方仓库与商店政策需要单独评估。

## 候选方案

| 方案 | 优点 | 代价/风险 | 验证结果 |
| --- | --- | --- | --- |
| A：明确不承诺完整 Linux；P2 再评估独立威胁模型与发行政策 | 预期诚实；不扩大 P0 攻击面；资源可控 | 部分进阶用户不满足；需要清楚的产品文案 | 采用；写入 README/`docs/CONTEXT.md` 的“非目标” |
| B：集成 Termux 作为外部依赖（Intent 跳转） | 复用生态与工具链 | 跨应用数据/权限边界；用户数据与学习闭环不可控；无法保证体验一致 | 不采用；最多在文档中提示“可自行安装第三方工具”，不集成、不背书 |
| C：内嵌 Linux 发行版（proot/chroot/VM） | 完整能力 | 体积/内存/安全/许可/商店政策全部冲突；本机 proot 环境本身无法作为可信边界 | 不采用 |
| D：P2 提供“受限 Linux 子集”（少量编译/运行能力） | 折中 | 仍需独立沙箱、原生依赖与许可评估；在没有威胁模型前不应实现 | 推迟；P2 单独 ADR |

## 决策

1. **明确非目标**：MVP 及 M1/M2 交付中不包含完整 Linux、Termux 集成、apt/包管理、系统 PTY、任意二进制执行。README、引导页、终端页帮助文案必须如实说明“内置安全命令，不是完整 Linux”。
2. **P2 才评估**：若未来评估 Linux 能力，必须提交独立 ADR + 威胁模型，至少覆盖：网络出口、子进程与 PTY、文件系统范围、原生依赖与 ABI、资源限制（CPU/内存/存储/时长）、第三方许可与再分发、商店政策、数据与隐私、卸载与回滚。
3. **不与 safe-shell 混合**：任何 Linux 运行时都必须作为独立 `RuntimePlugin`（`RuntimeKind` 新增值）接入，不能放宽 safe-shell 的路径、命令与资源约束。
4. **不集成 Termux 应用**：不通过 Intent、ContentProvider 或共享目录依赖 Termux 的运行时与数据；用户自行使用第三方应用属于应用外行为，CodeTree 不读取其数据、不宣称兼容。
5. **文档一致性**：`docs/CONTEXT.md`、README、PRD 的“非目标”与终端帮助文案必须与本 ADR 一致；如果未来状态变化，先修订本 ADR 再改产品文案。

## 理由

- P0 安全模型的前提是“没有任意代码执行”。完整 Linux 与 safe-shell 的约束直接冲突，不能靠“用户自己负责”绕过 `docs/07` 的门禁。
- 在本机 aarch64 proot 上都无法建立可信隔离，移动端普通应用更不具备；承诺完整 Linux 会制造无法兑现的安全与体验预期。
- 将 Linux 能力独立成 `RuntimePlugin`，可以在未来以增量方式接入，不污染现有终端与插件契约。

## 后果

### 正面

- 产品叙事诚实：学习闭环与受控实践是核心，不承诺不存在的 Linux 能力。
- 安全边界不被稀释，P0 安全测试范围明确。
- 资源与体积可控，符合低端设备目标。

### 负面与限制

- 进阶用户可能认为终端能力有限；需要通过示例、帮助与“为什么这样设计”的说明降低挫败。
- 未来若接入 Linux，需要额外的工程与安全投入，且可能与低端设备目标冲突。

### 对其他模块的影响

- `RuntimeKind` 未来可能新增 `TERMUX`/`LINUX` 值，但当前不注册、不可用；UI 不展示不存在的能力。
- 内容与示例不得假设系统包管理或任意命令存在；示例需标注“仅阅读”或“可在内置终端运行”。
- 发布说明与商店描述不得出现“完整 Linux 终端”等表述。

## 兼容与迁移

- 本 ADR 是产品能力边界声明，不涉及数据迁移；未来接入 Linux 时，新增运行时标识与迁移不影响既有内容 ID 与插件格式。
- 回滚条件：无（本决策为不承诺）；若未来决策变化，以新 ADR 替代本 ADR 并在 README/CONTEXT 同步更新。

## 验证计划

- 文档审计：README、PRD 非目标、终端帮助文案、`docs/CONTEXT.md` 均无“完整 Linux/系统 shell/apt 可用”等误导表述。
- 行为验收：终端帮助命令 `help` 明确列出白名单命令与“无管道/重定向/后台任务”的说明。
- 推翻条件：P2 商业决策要求提供 Linux 能力，且独立威胁模型与发行政策获批。
